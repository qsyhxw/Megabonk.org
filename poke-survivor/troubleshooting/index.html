Find the failure stage first

Identify what stopped: loading, one input, the run clock, frame rate, saving or the co-op connection. Preserve existing progress before refreshing or clearing anything. The dated reports below help narrow the next check; they are not universal fixes.

By Megabonk.org editors · Checked October 26, 2026 · Source-based; no comparative gameplay test

Dated reports from the original project

Extreme viewport: enemies appear to stop

bbbbbb123 reported enemy recycling outside the visible area at a very unusual 1587×188 window on October 26 (#350), with a source-based diagnosis. If your window is similarly extreme, return it to a conventional aspect ratio and compare what changes. This is a targeted check, not proof that all missing enemies have this cause; we did not reproduce the report.[3]

Visual animation continues, run clock stops

turbo012 reported a stopped clock and unresponsive inputs while some grass/water animation still moved on October 23 (#318). Record that distinction: moving visual effects alone do not prove the run is advancing. The report did not establish a universal repair.[4]

Low FPS when Arceus appears

DylanZM reported this on October 26 (#347). Note whether the clock continues and what happens before/after the transition. A demanding scene is a different symptom from a completely stopped simulation.[5]

Change one thing, preserve the comparison

  1. Note the game address, displayed version and exact stage.
  2. Check the game’s current graphics/control settings; change one option at a time so the comparison means something.
  3. If the viewport is extremely wide or short, try an ordinary shape.
  4. If only touch input fails, follow that symptom branch rather than assuming graphics settings repair it.
  5. Before any reload, inspect Save and acknowledge that an unfinished battle is not guaranteed to resume.

The creator documents settings and supported input routes, but that is not a minimum-device specification, measured FPS promise or diagnosis of your device.[6]

What to include in an actionable report

Use JPTER78’s GitHub issue tracker ↗ (external website, opens in a new tab) for the original game. Include the full game address, version, device/OS/browser, viewport or orientation, run time, selected partner/move, actions immediately before failure, and whether menus, clock, audio and visual animation still work. If relevant, identify host versus guest.

Say which checks changed the symptom and which did not. Include no passwords, cookies or account tokens. A report remaining open means its outcome was not established here; it is not evidence of a measured global failure rate.

Rules below refer to JPTER78’s source snapshot 680c3e12c670, reviewed October 26, 2026. Other hosted editions and native ports can differ. We have not completed a comparative run or verified a universal fix.
